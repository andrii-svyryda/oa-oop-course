# Відносини між об’єктами в C#

## На що звернути увагу

Під час вивчення цієї теми зверніть увагу на відмінності між асоціацією, композицією та агрегацією. Ви навчитеся розрізняти підходи «is-a» та «has-a», а також зрозумієте, коли краще використовувати композицію замість наслідування.

## Спробуйте самі

Спробуйте самостійно описати класи менеджера, робітника та проєктів, щоб на практиці побачити, як працюють зв’язки між об’єктами. Також реалізуйте структуру даних стек двома різними способами: спочатку через наслідування від `List<T>`, а потім — використовуючи композицію.

## Пов’язані лабораторні

- Практичні приклади з лекції теорії ООП (автосалон, гаманець) використовують композицію та асоціацію.

## Відношення між об’єктами: асоціація, агрегація, композиція

Розберіть зв’язки на класах **менеджер**, **робітник**, **проєкт**.

**Асоціація** — об’єкти знають один про одного і можуть взаємодіяти, але час життя не пов’язаний. Менеджер *керує* робітниками: видалення менеджера не знищує робітників.

**Агрегація** — «ціле і частини», але частина може існувати окремо від цілого. Проєкт (батько) і робітник (дитина): проєкт закрили — робітник лишається в компанії.

**Композиція** — сильніше володіння: частина не існує без цілого. Дім і кімната: без дому кімнати немає. У коді це зазвичай `private` поле, яке створюється всередині власника і не «витікає» назовні.

```csharp
public class Worker
{
    public string Name { get; }

    public Worker(string name) => Name = name;
}

public class Project
{
    // агрегація: робітники живуть і поза проєктом
    public List<Worker> Team { get; } = new();
}

public class Manager
{
    public string Name { get; }
    public List<Project> Projects { get; } = new(); // асоціація / агрегація

    public Manager(string name) => Name = name;
}

public class Company
{
    // композиція: організаційна структура не існує окремо від компанії
    private readonly List<Manager> _managers = new();

    public Manager HireManager(string name)
    {
        var manager = new Manager(name);
        _managers.Add(manager);
        return manager;
    }
}
```

## Композиція проти наслідування

На першій лекції ви вже навчилися будувати ієрархії, наприклад `Student : Person`. А сьогодні ви побачите, що композиція — це не лише про те, «хто кого створює», а ще й чудовий спосіб **перевикористати поведінку**.

**Наслідування (is-a).** Ваш нащадок *є* батьком. Ви отримуєте весь його публічний та `protected` API. Пам’ятайте, що в C# дозволений лише один базовий клас. Зате поліморфізм працює одразу: ви можете створити `List<Shape>` і покласти туди різні фігури.

**Композиція (has-a).** Ваш об’єкт *має* інший об’єкт і просто делегує йому частину роботи. Скажімо, автомобіль має двигун, але він сам не є двигуном. Тут ви самі вирішуєте, які методи варто показати назовні, і за потреби можете легко замінити цю внутрішню деталь.

### Коли наслідування шкодить

Класична пастка, у яку легко потрапити: зробити стек нащадком списку.

```csharp
class InheritedStack<T> : List<T>
{
    public void Push(T item) => Add(item);

    public T Pop()
    {
        var item = this[^1];
        RemoveAt(Count - 1);
        return item;
    }
}

var stack = new InheritedStack<int>();
stack.Push(1);
stack.Push(2);
stack.Insert(0, 99); // список дозволяє. Стек — ні.
```

Ваш `InheritedStack` формально *є* списком (`List`), тож клієнт спокійно бачить `Insert`, `RemoveAt` та індексатор. Усе, інваріант LIFO вам більше не належить — його легко зламати.

Так само ніколи не пишіть `class Car : Engine`. Машина не є двигуном.

### Коли композиція рятує

```csharp
class ComposedStack<T>
{
    private readonly List<T> _items = new();

    public void Push(T item) => _items.Add(item);

    public T Pop()
    {
        var item = _items[^1];
        _items.RemoveAt(_items.Count - 1);
        return item;
    }

    public int Count => _items.Count;
}
```

Тут список — це лише прихована деталь імплементації. Ззовні ви віддаєте лише те, що стек дійсно обіцяє робити.

```csharp
class Engine
{
    public string Start() => "vroom";
}

class Car
{
    private readonly Engine _engine = new();
    public string Drive() => $"{_engine.Start()}, їдемо";
}
```

### Плюси й мінуси

| | Наслідування | Композиція |
|---|---|---|
| Плюси | Поліморфізм працює без зайвого коду (якщо правило is-a дійсно виконується). | Ви повністю контролюєте API, легко замінюєте частини та комбінуєте ролі без множинного наслідування. |
| Мінуси | Крихкий базовий клас, ви тягнете зайвий API, дозволений лише один батько, і нащадка важче тестувати ізольовано. | Доведеться делегувати методи; сама по собі композиція не дає поліморфізму — для цього вам знадобиться спільний контракт. |

### Правило на іспит і в коді

1. Наслідуйте, лише якщо ваш нащадок дійсно **є** батьком у будь-яких сценаріях, і ви готові прийняти весь його API.
2. Інакше обирайте композицію: принцип «я використовую», а не «я є».
3. Якщо сумніваєтесь — завжди починайте з композиції. Неправильну ієрархію наслідування потім буде дуже важко розплутати.
4. А про те, чи можна безпечно підставити нащадка замість батька без поломки — ми детально поговоримо на четвертій лекції (це принцип **LSP**).
