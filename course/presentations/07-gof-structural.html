Структурні патерни GoF

Як збирати класи разом: обгортки, спрощені фасади й дерева однотипних вузлів.

Декоратор

Як додати нову поведінку, не чіпаючи старий код? Просто обгорніть його.

Ми зберігаємо той самий контракт, але додаємо щось своє до або після виклику.

  • Це ідеально підходить для retry, логування, кешу чи шифрування.
  • Ви можете нанизувати їх рекурсивно: декоратор на декоратор.
  • Клієнт навіть не здогадується, що працює з обгорткою, а не з оригіналом.

Декоратори над IMessenger

Можемо додати логування чи повторні спроби, обгорнувши базовий месенджер.

public interface IMessenger {
  void Send(Message message);
  Message Receive();
}
// LoggingMessenger : IMessenger
// RetryMessenger : IMessenger
// обидва тримають inner IMessenger всередині себе

Фасад

Сховайте складну підсистему за єдиним простим класом.

  • Ви даєте клієнту простий інтерфейс замість десятка складних.
  • Наприклад, метод PlaceOrder сам викличе і Product, і Payment, і Invoice.
  • Клієнту більше не треба збирати цю оркестрацію вручну.

Adapter і Composite

Ще два корисних інструменти для побудови структури.

Adapter

У вас є чужий інтерфейс, а вам потрібен ваш контракт. Наприклад, ви адаптуєте стару бібліотеку логування під сучасний ILogger.

Composite

Дозволяє працювати з окремим об’єктом і групою об’єктів однаково. Наприклад, IGraphic може бути як одним колом (Circle), так і групою фігур (GroupOfGraphics).

Як обрати потрібний патерн

Правила-маркери:

  • Хочете додати поведінку навколо існуючого об’єкта непомітно для інших? Беріть Decorator.
  • Клієнту доводиться смикати занадто багато класів для однієї дії? Сховайте їх за Facade.
  • Маєте два несумісні інтерфейси, які треба подружити? Пишіть Adapter.
  • Будуєте дерево елементів, де гілка поводиться так само, як листок? Це Composite.
