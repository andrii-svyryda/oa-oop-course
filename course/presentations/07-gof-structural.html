Робота зі створеними об'єктами

Якщо породжувальні патерни вирішували проблеми створення об'єктів, то структурні фокуються на їх компонуванні. Ми дізнаємося, як гнучко розширювати функціонал через обгортки, адаптувати несумісні інтерфейси та будувати складні ієрархії.

Декоратор (Decorator)

Ми додаємо нову поведінку навколо того самого контракту, не чіпаючи оригінальний клас.

  • Клієнт викликає IMessenger і не здогадується, що перед ним обгортка.
  • Коли: треба динамічно додати логування, retry, кеш чи шифрування, нанизуючи їх один на одного.
  • Уникайте, коли: порядок нанизування обгорток має критичне значення, оскільки клієнт може легко помилитися під час їх конструювання. Крім того, наявність десятків дрібних декораторів перетворює код ініціалізації на величезну і нечитабельну "матрьошку". Відлагоджувати такий код стає дуже важко. Альтернатива: Патерн Стратегія (якщо є чіткі точки розширення).

Декоратори над IMessenger

Ви самі вирішуєте, як зібрати ланцюжок: спочатку логування, а потім retry, або навпаки.

public interface IMessenger {
  void Send(Message message);
  Message Receive();
}
// LoggingMessenger(inner)
// RetryMessenger(inner)
IMessenger m = new RetryMessenger(
  new LoggingMessenger(real));

Проксі (Proxy)

Це обгортка з тим самим контрактом, щоб контролювати доступ або ліниво створювати об’єкт.

class ImageProxy : IImage {
  private HeavyImage? _real;
  public void Draw() {
    _real ??= new HeavyImage(path);
    _real.Draw();
  }
}
  • Коли: потрібен лінивий доступ до важкого об'єкта, логування викликів, кешування або контроль прав доступу.
  • Уникайте, коли: приховування реальності грає проти вас. Проксі має той самий інтерфейс, що й оригінал, тому клієнт очікує швидкого виконання. Якщо ваш проксі під капотом робить важкі мережеві запити, клієнт отримає непередбачуване зависання програми. Краще робити такі важкі операції явно. Альтернатива: Асинхронні методи, явний Фасад або пряме створення.

Decorator додає нову фічу, а Proxy вирішує, чи і коли пустити виклик далі.

Адаптер (Adapter)

Коли чужий інтерфейс не підходить, ви пишете адаптер, який перекладає виклики на ваш контракт.

class LegacyLog { public void WriteLine(string x) {} }

class LoggerAdapter : ILogger {
  private readonly LegacyLog _old;
  public LoggerAdapter(LegacyLog old) => _old = old;
  public void Log(string msg) => _old.WriteLine(msg);
}
  • Коли: треба використати існуючий клас (наприклад, сторонню бібліотеку чи застарілий код), але його інтерфейс не збігається з вашим контрактом.
  • Уникайте, коли: ви є власником обох інтерфейсів і маєте доступ до їхнього коду. Замість того, щоб будувати "милиці" у вигляді класів-адаптерів і плодити зайві абстракції, набагато ефективніше провести рефакторинг старого коду і звести все до єдиного стандарту. Альтернатива: Рефакторинг оригіналу.

Фасад (Facade)

Коли підсистема занадто складна, ми даємо клієнту одні прості двері для взаємодії з нею.

  • Facade не додає нових фіч навколо одного об’єкта — він приховує від вас цілу групу класів (Product, Payment, Invoice).
  • Коли: потрібен простий та зрозумілий інтерфейс до складної підсистеми з багатьма класами.
  • Уникайте, коли: Фасад бере на себе занадто багато відповідальності та починає керувати абсолютно всіма процесами. З часом він перетворюється на "божественний об'єкт" (God Object), який має сотні методів. Будь-яка зміна в програмі вимагатиме зміни цього Фасаду. Альтернатива: Розділити систему на кілька вужчих сервісів або використати Медіатор.

Компонувальник (Composite)

Він дозволяє дати і листку, і групі об’єктів однаковий інтерфейс. Ви будуєте дерево (наприклад, група кіл).

interface IGraphic { void Draw(); }
class Circle : IGraphic { public void Draw() { } }
class Group : IGraphic {
  private readonly List<IGraphic> _items = new();
  public void Add(IGraphic g) => _items.Add(g);
  public void Draw() { 
    foreach (var g in _items) g.Draw(); 
  }
}
  • Коли: об'єкти мають деревоподібну структуру і клієнту зручно працювати з цілим деревом як з одним об'єктом.
  • Уникайте, коли: відмінностей між "листком" і "групою" занадто багато. Щоб мати спільний інтерфейс, вам доведеться додати методи типу AddChild() у базовий контракт. Тоді звичайний листок (наприклад, коло) муситиме їх реалізовувати і кидати NotSupportedException, що грубо порушує принципи ISP та LSP. Альтернатива: Звичайні колекції List<T> без об'єднання загальним інтерфейсом.

Не плутайте обгортки

  • Decorator — зберігає той самий контракт, але додає нову поведінку, наприклад, логування чи retry.
  • Proxy — також зберігає контракт, але контролює доступ до об’єкта або момент його створення.
  • Adapter — дозволяє вам зробити інший, чужий контракт своїм.
  • Facade — дозволяє нам сховати багато складних класів за одним простим.

Коли який

  • Якщо вам потрібно нанизати retry або лог на існуючий сервіс — беріть Decorator.
  • Якщо ви не хочете вантажити важкий об’єкт, доки вас про це не попросять — використовуйте Proxy.
  • Якщо перед вами стара бібліотека з чужим API — пишіть Adapter.
  • Коли дія одна, а всередині десять класів — вам потрібен Facade.
  • А якщо ви будуєте дерево з однотипних вузлів — це Composite.
