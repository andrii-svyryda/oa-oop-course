Впровадження залежностей

Не створюйте сервіс самі — отримайте його ззовні.

IoCTransientScopedSingleton

Щільне зв’язування

Зміна логера змушує чіпати MessageProcessor.

public class MessageProcessorForTightCoupling {
  private LogManager logManager;
  public MessageProcessorForTightCoupling() {
    this.logManager = new LogManager(); // сам створив
  }
}

Слабке зв’язування і DI

  • Створення об’єктів відокремлене від їх використання
  • Клієнт не знає, як зібрати сервіс
  • Залежність передають (constructor / method / property injection)
  • DI ≠ DIP, але DI — типовий спосіб дотримати DIP

Контейнер Microsoft.Extensions.DependencyInjection

using IHost host = Host.CreateDefaultBuilder()
  .ConfigureServices((_, services) => {
    services.AddSingleton<IEmailNotification, EmailNotification>();
    services.AddSingleton<NotificationService>();
  }).Build();

var sender = host.Services.GetService<NotificationService>();
sender.PushNotification("DI is not DIP");

Service lifetimes

Lifetime підказує контейнеру, як довго житиме екземпляр після GetService.

Transient

Щоразу новий об’єкт. Два GetService підряд дадуть різні Guid.

Scoped

Один об’єкт на scope. У вебі один scope — це один HTTP-запит. У консолі ви створюєте scope самі.

Singleton

Один об’єкт на весь застосунок. Усі ваші scope бачать той самий екземпляр.

Як побачити різницю

Кожен сервіс у конструкторі запам’ятовує свій Guid. Порівняйте їхні ідентифікатори.

services.AddTransient<ITransientOp, Operation>();
services.AddScoped<IScopedOp, Operation>();
services.AddSingleton<ISingletonOp, Operation>();

using var scope1 = provider.CreateScope();
using var scope2 = provider.CreateScope();
// у scope1 два Transient — різні
// у scope1 два Scoped — однакові
// Scoped у scope1 і scope2 — різні
// Singleton у scope1 і scope2 — один і той самий

Transient

  • Легка робота без спільного стану: мапер, калькулятор, «зробили й забули».
  • Безпечно передавати в будь-який інший сервіс, адже він живе недовго.
  • Не кладіть туди кеш чи підключення до БД, бо ви створюватимете їх на кожен виклик.

Scoped

  • Один «контекст» на одну справу: DbContext, поточний користувач, unit of work.
  • У ASP.NET Core контейнер відкриває scope на кожен HTTP-запит самостійно.
  • У консолі ви відкриваєте його так: using var scope = host.Services.CreateScope();
  • Не резолвіть Scoped з кореня без scope, інакше отримаєте warning або виняток.

Singleton

  • Спільне на весь процес: конфіг, кеш у пам’яті, фабрика HttpClient.
  • Створюється ліниво, при першому запиті (або одразу, якщо ви реєструєте готовий екземпляр).
  • Він має бути thread-safe, бо ним користуються всі потоки одразу.
  • Не захоплюйте Scoped чи Transient у конструктор Singleton — це captive dependency.

Captive dependency

Довгоживучий сервіс «бере в полон» короткоживучий. Ваш Scoped тоді житиме стільки ж, скільки й Singleton — тобто весь час роботи застосунку.

services.AddScoped<IOrderDb, OrderDb>();
services.AddSingleton<OrderCache>(); // ctor(IOrderDb db) — погано

// OrderCache створиться раз і триматиме один OrderDb назавжди.
// Другий HTTP-запит побачить чужі дані.

Правило: залежність живе не довше за свого власника. Singleton ← лише Singleton. Scoped ← Scoped або Singleton. Transient ← будь-що.

Де можна писати new

  • Писати в бізнес-класі new LogManager() чи new EmailNotification() — погана ідея. Так клас знову сам збирає свої залежності.
  • Усе зшивання графа об’єктів робимо в одному місці: у Program (або Startup для вебу). Це так званий composition root.
  • Саме там ви реєструєте сервіси в контейнері. А далі конструктор або GetService отримують уже готові об’єкти.
  • Використовувати new для дрібниць ніхто не забороняє: List<T>, рядки, Guid.NewGuid(), DTO. Ми говоримо про сервіси з поведінкою, а не про прості дані.
