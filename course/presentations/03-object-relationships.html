Відносини між об’єктами

Розбираємося, хто ким володіє — і коли вам краще заховати об’єкт усередині, а не наслідувати його.

Три типи зв’язку

Наскільки об’єкти залежать один від одного?

Асоціація

Вони просто знають одне про одного, але їхній час життя не пов’язаний. Скажімо, менеджер керує робітниками. Звільнили менеджера — робітники продовжують працювати.

Агрегація

Тут ми вже маємо ціле та його частини, але частина може існувати окремо. Проєкт закрили — робітник просто переходить на інший, він лишається в компанії.

Композиція

Найжорсткіший зв’язок: частина не існує без цілого. Зруйнували дім — зникла й кімната. У коді це зазвичай private поле, яке ви створюєте прямо всередині власника.

Як це виглядає в коді

Погляньте, хто кого створює.

public class Project {
  public List<Worker> Team { get; } = new(); // агрегація: ми просто додаємо існуючих робітників
}

public class Company {
  private readonly List<Manager> _managers = new(); // композиція: компанія сама створює менеджерів
  public Manager HireManager(string name) {
    var m = new Manager(name);
    _managers.Add(m);
    return m;
  }
}

Як розрізнити їх на іспиті

Ось кілька простих запитань, щоб ви не заплуталися:

  • Хто створює об’єкт? Якщо власник робить це сам — скоріш за все, перед вами композиція.
  • Чи можете ви передати цю частину в інше ціле? Якщо так — це агрегація або асоціація.
  • Як це малювати на UML? Композиція — це зафарбований ромбик, а агрегація — порожній.

is-a чи has-a?

Наслідування з першої лекції та сьогоднішня композиція — це просто два різні способи перевикористати код.

Наслідування — is-a

  • Студент є людиною. Квадрат є фігурою.
  • Ваш нащадок отримує весь публічний і захищений API батька — навіть ті методи, які вам зовсім не потрібні.
  • У C# дозволений лише один батьківський клас. Змінили базу — ризикуєте зламати всіх нащадків.

Композиція — has-a

  • Автомобіль має двигун. Але він сам не є двигуном.
  • Тут ви самі вирішуєте, які методи варто прокинути назовні клієнтам.
  • Ви можете легко замінити частину: підставити інший двигун, інший логер або інакший список усередині.

Погано: Stack наслідує List

Стек насправді не є списком. Якщо ви унаслідуєте List<T>, ваш клієнт викличе Insert десь посередині й зламає вам усю логіку LIFO.

class InheritedStack<T> : List<T> {
  public void Push(T item) => Add(item);
  public T Pop() { var x = this[^1]; RemoveAt(Count - 1); return x; }
}

var s = new InheritedStack<int>();
s.Push(1); s.Push(2);
s.Insert(0, 99); // стек це дозволяє. Не повинен.

Добре: Stack тримає List

Список лишається лише деталлю імплементації. Назовні ви віддаєте тільки Push, Pop та Peek.

class ComposedStack<T> {
  private readonly List<T> _items = new();
  public void Push(T item) => _items.Add(item);
  public T Pop() {
    var x = _items[^1];
    _items.RemoveAt(_items.Count - 1);
    return x;
  }
}

Плюси й мінуси

Наслідування

  • Поліморфізм працює «з коробки»: ви робите колекцію Shape і кладете туди різні фігури.
  • Ви пишете менше коду, якщо правило is-a дійсно виконується.
  • Крихкий базовий клас: одна правка батька може вдарити по всіх нащадках.
  • Ви тягнете за собою зайвий API. У вас лише один батько, і нащадка важче тестувати ізольовано.

Композиція

  • Ви повністю контролюєте публічну поверхню. Легко підмінити деталь і плавно дійти до DI.
  • Ви можете зібрати докупи кілька поведінок і без множинного наслідування.
  • Доведеться писати трохи більше коду, адже вам потрібно делегувати виклики методів.
  • Сама по собі вона не дає поліморфізму — для цього вам знадобиться спільний контракт.

Коли що брати

  • Наслідуйте, лише якщо ваш нащадок дійсно є батьком у будь-яких сценаріях, і ви готові прийняти весь його API. Трохи згодом це формалізує LSP на четвертій лекції.
  • Композиція — це ваш типовий вибір за замовчуванням: «я використовую», а не «я є». Авто має двигун, стек має список.
  • Якщо сумніваєтесь — завжди починайте з композиції. Наслідування потім буде дуже важко вичистити з коду.

Місток до DI

Зверніть увагу: якщо ваш об’єкт не створює залежність сам, а отримує її ззовні — ви послаблюєте зв’язок до асоціації. Це ваш перший крок до впровадження залежностей (DI).
